# HomeHub V5 — Firestore Schema

Status: **Phase 1 (Foundation) + Phase 2 (Rooms) + Phase 3 (Devices) + Phase 4 (Finance)**. `schemaVersion: 1` for every document type.

Every path is built in one place: `src/core/firebase/paths.js`.
Collections are **not** pre-created. They appear when the first real document is written.

## Implemented now

```
users/{uid}                                  identity + personal preferences (private)
homes/{homeId}                               home identity + core locale settings
homes/{homeId}/members/{uid}                 MEMBERSHIP — the authorization source
homes/{homeId}/roles/{roleId}                role → permission grants (5 seeded)
homes/{homeId}/settings/general              home-wide general settings
homes/{homeId}/rooms/{roomId}                Phase 2 — rooms of the home (created by users only)
homes/{homeId}/devices/{deviceId}            Phase 3 — devices & household assets (roomId → rooms)
homes/{homeId}/wallets/{walletId}            Phase 4 — household & personal wallets (privacy)
homes/{homeId}/expenses/{expenseId}          Phase 4 — money spent (incl. imported CSV history)
homes/{homeId}/walletMovements/{id}          Phase 4 — funding / transfer / adjustment (never spending)
homes/{homeId}/spendingCycles/{cycleId}      Phase 4 — rolling N-day budgets on one wallet
homes/{homeId}/commitments/{commitmentId}    Phase 4 — fixed / recurring obligations (templates)
```

First-time setup writes exactly these 9 documents in **one atomic batch**:
`homes/{h}`, `members/{uid}`, `roles/{owner,admin,member,viewer,child}`, `settings/general`, `users/{uid}`.

### homes/{homeId}/rooms/{roomId}  — Phase 2

`roomId` is generated by Firestore and is **permanent**. Rooms are never hard-deleted.

| Field | Type | Notes |
|---|---|---|
| name | string (1–60, trimmed) | User's own name, independent of type ("Main Kitchen") |
| type | enum id | One of `living_room, bedroom, master_bedroom, kids_room, kitchen, bathroom, dining_room, office, balcony, laundry, storage, garage, garden, hallway, entrance, other`. Translated in the UI (`rooms.type.<id>`), never stored translated |
| icon | icon id `^[a-z][a-z0-9_]{0,31}$` | `sofa, bed, kids, kitchen, bath, dining, office, plant, laundry, storage, garage, garden, door, lamp, stairs, tv, gym, prayer, home`. Unknown ids fall back to the type's icon, then 🏠 |
| floor | string (1–40) \| null | Optional free-text floor/area in the user's words. No Floors entity |
| notes | string (1–500) \| null | Optional |
| sortOrder | int 0 – 1,000,000,000 | Display order. Ties broken by name, then id |
| active | bool | `false` = archived (soft delete) |
| archivedAt | timestamp \| null | Set on archive, cleared on restore |
| archivedBy | uid \| null | Set on archive, cleared on restore |
| createdBy | uid | `== request.auth.uid` on create, immutable |
| createdAt | timestamp | Server time, immutable |
| updatedBy | uid | `== request.auth.uid` on every write |
| updatedAt | timestamp | Server time on every write |
| schemaVersion | int | `1`, immutable |

Changes from the brief's suggested schema:
- **Added `archivedAt` / `archivedBy`.** These record who archived a room and when, without a separate log.
- **`sortOrder` is an integer.** Integers are easy to validate in rules; a move renumbers the active rooms 1..n in one batch.

**Deliberately absent:**
- No `devices: []` or any other child array. Children point to their room.
- No `homeId` field; the path is the tenant boundary.

Ordering:
- New rooms take `max(sortOrder of all rooms, including archived) + 1`.
- Move earlier/later renumbers active rooms 1..n in the new order. Only changed documents are written, in one atomic batch, which also repairs duplicates left by concurrent creates.
- Restore appends the room to the end.

Archive strategy:
- "Delete" sets `active:false`, `archivedAt`, `archivedBy`. The document and its id remain, so future references still resolve.
- Archived rooms are read-only (rules) until restored.

Reads: the client listens to the whole `rooms` collection (no `where`/`orderBy`), then filters and sorts client-side. **No composite index is required** (`firestore.indexes.json` unchanged). One listener per signed-in Home is shared by the Rooms page and the Dashboard widget.

### homes/{homeId}/devices/{deviceId}  — Phase 3

`deviceId` is generated by Firestore and is **permanent**. It never changes on rename, move, category change, archive or restore. It is never derived from the serial number, model, name or room. Devices are never hard-deleted.

| Field | Type | Notes |
|---|---|---|
| name | string (1–80, trimmed) | |
| category | enum id | 19 ids: `air_conditioning, refrigeration, laundry, kitchen_appliance, water_system, audio_video, computing, networking, cleaning_equipment, lighting, electrical, power, heating, ventilation, plumbing, security, furniture, outdoor, other` |
| subtype | id \| null | Must belong to the category (see `DEVICE_CATEGORIES` in `device-model.js`; rules hold the same map). `other` allowed where the category has subtypes |
| roomId | room id \| null | **null = Unassigned.** Points to `homes/{homeId}/rooms/{roomId}` of the same home |
| status | enum | `operational` (Working), `needs_attention`, `out_of_service`, `stored`. Descriptive only; it triggers nothing |
| icon | icon id | 29 ids; unknown ids fall back to subtype → category → ⚙️ |
| brand, model | string (1–60) \| null | |
| serialNumber | string (1–80) \| null | **Not unique**, never an id |
| purchaseDate, installationDate, warrantyExpiry | `'YYYY-MM-DD'` \| null | Calendar dates as strings (see below) |
| purchasePrice | number ≥ 0 (≤ 1e12, ≤ 2 decimals in the UI) \| null | Asset metadata, **not** an expense. 0 is a real price; null means none |
| currency | ISO code \| null | Required when there is a price, null otherwise. Defaults to the Home currency in the form and is **snapshotted**, so the price stays meaningful if the Home currency changes later |
| notes | string (1–1000) \| null | |
| active, archivedAt, archivedBy | | Same soft-archive pattern as rooms |
| createdBy, createdAt, updatedBy, updatedAt, schemaVersion | | Same audit pattern as rooms; `schemaVersion: 1` |

Review of the brief's suggested schema:
- **Kept:** every field except `sortOrder`.
- **Dropped `sortOrder`.** Devices are sorted by name, room, category or status, and filtered, so there's no manual ordering to store. This avoids schema inflation.
- **Not added:** `warrantyProvider`, photos, documents, or any cleaning, maintenance or expense fields.

**Dates.** Date-only values are stored as `'YYYY-MM-DD'` strings, never as Firestore Timestamps or JS Dates. A Timestamp is an instant, so a date like 2027-06-30 at midnight in Cairo would read as 06-29 in UTC-based code. The UI uses `<input type="date">` (which already yields `YYYY-MM-DD`) and formats in UTC for display. The model rejects impossible dates such as Feb 30. Rules enforce the format and range (1900–2100), but can't check calendar validity.

**Room relationship.**
- Devices are Home-level and *reference* rooms. Rooms never embed devices.
- Archiving a room changes **nothing** on its devices: they keep `roomId`, and the UI shows "Bedroom (Archived)".
- A *new* assignment (create, or a changed `roomId`) must target an existing **active** room of the same home. An *unchanged* reference to an archived room stays valid, so you can still edit a device's other fields.
- A device can be moved to an active room or to Unassigned at any time.

**Reads.** One whole-collection listener per Home, with client-side search, filters and sort. **No composite index required.**

**Future contracts (not implemented):**
- Cleaning tasks: `{ targetType: 'device', deviceId }` or `{ targetType: 'room', roomId }`.
- Maintenance records: `{ assetType: 'device', deviceId }` (optionally `roomId`).
- Expenses created from maintenance: `{ sourceType: 'maintenance', sourceId }`.
- History stays resolvable because archived devices and rooms are kept.
- Device documents will **never** hold `maintenanceHistory`, `nextMaintenanceDate`, `lastCleaned`, `cleaningFrequency` or expense links; those belong to their modules.
- Photos, manuals, receipts and warranty documents are future Storage-backed features. Base64 in Firestore is not allowed.

## Finance (Phase 4)

### Conventions
- **Money:** integer **minor units** (`amountMinor`; 12345 = 123.45 EGP). No floats anywhere. Rules require `int`.
- **Dates:** `'YYYY-MM-DD'` strings (`date`, `startDate`, `nextDueDate` …); "today" uses the Home time zone.
- **Currency:** explicit on every wallet and record. There is no conversion: transfers between different currencies are refused.
- **No hard deletes.** Expenses and movements are *voided* (`status: 'void'`, `voidedAt`, `voidedBy`, `voidReason`) and kept in history. Wallets and commitments are archived. Cycles are closed.
- **Access labels on every record:** `audience: 'household' | 'restricted'` + `readers: [uid]`, always derived from the wallet(s) involved (see SECURITY.md).

### wallets/{walletId}
`name, type (cash|bank|card|digital|allowance|other), scope (home|personal), ownerUid (personal only), visibility (household|private|shared), sharedWith [≤5 member uids], readers (= [] for household, owner + sharedWith for personal), currency, active, archivedAt, archivedBy, createdBy, createdAt, updatedBy, updatedAt, schemaVersion`.
A wallet's balance is **computed**, never stored: Σ movements in − Σ movements out − Σ active expenses.

### expenses/{expenseId}
`amountMinor (>0), currency, date, category, note, merchant, paymentMethod (cash|debit_card|credit_card|bank_transfer|digital_wallet|other; 'visa' only on imported history), walletId|null, budgetCycleId|null, paidBy|null (who paid; may differ from createdBy), commitmentId|null, commitmentDueDate|null, audience, readers, status, voidedAt, voidedBy, voidReason, source ('app'|'import'), createdBy, createdAt, updatedBy, updatedAt, schemaVersion`.
- Imported history additionally has `importedCategory` (original text), `importBatchId`, and `originalRow` (every CSV column verbatim). `walletId` is null and the audience is household. Document ids are the CSV's own ids (or a stable hash of the row).
- **Fixed vs variable:** an expense with `commitmentId` is a fixed-commitment payment; otherwise variable.
- **Commitment payment id:** `cm_{commitmentId}_{YYYYMMDD of the due date}`, so it is deterministic and can't be duplicated.

### walletMovements/{movementId}
`type (funding|transfer|adjustment), amountMinor (>0), currency, date, fromWalletId|null, toWalletId|null, cycleId|null, note, audience, readers, status, voidedAt, voidedBy, + audit`.
- **funding:** outside → wallet (opening balance, salary, gift). **transfer:** wallet → wallet, same currency (e.g. a bank withdrawal into cash). **adjustment:** cash-count difference, ±, on one wallet.
- **Never counted as spending or income.** Future Life-Savings transfers (wallet ↔ savings) reuse this model.

### spendingCycles/{cycleId}
`walletId, currency, startDate, endDate, days (1–31, default 10), budgetMinor, carryInMinor, previousCycleId, status (active|closed), closedAt, closedBy, closeOutcome (carry|return|keep), closingRemainingMinor, nextCycleId, audience, readers, + audit`.
- Cycles are rolling and flexible, not calendar thirds. At most one active cycle per wallet (enforced in the app).
- Expenses link via `budgetCycleId`. New expenses auto-link to the wallet's active cycle when their date falls inside it.
- The figures are computed, never stored:
  - **remaining** = budget + carryIn − spent + adjustments;
  - **safe/day** = remaining ÷ days remaining;
  - **pace** = spent − available × elapsed/days.

### commitments/{commitmentId}
`name, amountMinor, currency, category, recurrence {unit: day|week|month|year, interval 1–36}, anchorDay (1–31), nextDueDate, paymentMethod, walletId|null (preferred), notes, lastPaidDate, audience, readers, active, archivedAt, archivedBy, + audit`.
- Weekly, every 2 weeks, monthly, quarterly, every 6 months, annual, every 2 years and custom intervals all use the same engine.
- Month and year steps keep `anchorDay` (31 Jan → 28 Feb → 31 Mar).
- A commitment is a **template, not an expense**. "Mark paid" writes the payment expense and advances `nextDueDate` in one atomic batch.
- Suggested monthly reserve = amount × occurrences per year ÷ 12. It's computed only, ready for a future sinking-fund feature.

### Indexes
None. Every finance listener uses a single-field constraint (`audience == 'household'`, `visibility == 'household'`, or `readers array-contains uid`), which Firestore indexes automatically. Totals are computed client-side over the full permitted collections; there is no pagination, so totals stay exact. That suits household scale: hundreds to a few thousand expenses.

### Future (Phase 5, NOT implemented)
- Life Savings: `homes/{h}/savings/{id}` (cash, bank, gold, silver, FX, investments), same `scope / ownerUid / visibility / readers` privacy model.
- Valuations: from a replaceable price-provider interface; never an LLM.
- Zakat: `homes/{h}/zakat/…` with a configurable nisab method (default 85 g of 21k gold; silver alternative), Hijri hawl and payment history.
- Wallet ↔ savings moves are `walletMovements` transfers, never income or expense.

## Cross-module reference conventions (for future modules)

Modules link by **stable document ids**, never by copying another module's data.

| Field | Meaning | Example |
|---|---|---|
| `createdBy`, `updatedBy` | uid of the writer | every business document |
| `createdAt`, `updatedAt` | server timestamps | every business document |
| `<entity>Id` | a direct, required parent link | `devices/{id}.roomId` |
| `sourceType`, `sourceId` | the record that *caused* this one | expense: `sourceType: 'maintenance'`, `sourceId: <maintenanceId>` |
| `linkedEntityType`, `linkedEntityId` | a non-owning association | cleaning task: `linkedEntityType: 'device'` |
| `schemaVersion` | per-collection document version | |

Planned relationships: Room → Device → (Cleaning, Maintenance → Expense). Recipe → Ingredients → (Inventory, Shopping). Dashboard ← summaries from every module.

A denormalised copy (like `members.displayName`) is allowed only with a written reason, and must have exactly one writer that keeps it in sync.

## Indexes

None needed in Phases 1–4 (`firestore.indexes.json` is empty). Rooms and devices are each read as a whole collection without query constraints; search, filters and sort run client-side.

## Phase 5.3 collections (all under `homes/{homeId}/`)

### budgetAdjustments/{cycleId}_r{revision}  (append-only)
`cycleId`, `walletId`, `revision` (int ≥ 1), `oldBudgetMinor`, `newBudgetMinor`, `deltaMinor`, `currency`, `reason` (≤ 200 or null), `editorUid`, `createdAt` (server), `audience` / `readers` (copied from the cycle), `schemaVersion`.

**`spendingCycles` gains an optional `budgetRevision`** (int; missing = 0 on older cycles). Its dates and duration are immutable.

### cleaningTasks/{taskId}
`title` (≤ 80), `instructions` (≤ 1000 or null), `roomId` (or null), `priority` (`low` | `normal` | `high`), `assignMode` (`assigned` | `shared`), `assigneeUids` (assigned: 1–5), `eligibleUids` (shared: 0–5; [] = every adult), `recurrence`, `startDate`, `dueDate` (once only), `endDate` (or null), `active`, `archivedAt`, `archivedBy`, audit fields, `schemaVersion`.

`recurrence` takes one of these shapes:
- `{kind: 'once'}`
- `{kind: 'days', interval}`
- `{kind: 'weeks', interval, weekdays: [0..6]}`
- `{kind: 'months', interval, dayOfMonth: 1..31}`

### cleaningOccurrences/{taskId}_{YYYYMMDD}  (created only when someone acts)
`taskId`, `dueDate`, `status` (`claimed` | `done` | `open`), `rev` (int, +1 per change), `claimedBy` / `claimedAt`, `completedBy` / `completedAt`, `notes`, `createdAt`, `updatedBy`, `updatedAt`, `schemaVersion`.

### cleaningLog/{occurrenceId}_r{rev}  (append-only)
`occurrenceId`, `taskId`, `rev`, `action` (`claim` | `unclaim` | `complete` | `reopen`), `actorUid`, `at` (server), `notes` (reopen: required reason), `schemaVersion`.

### Phase 5.3.1 additions to `cleaningTasks` (optional fields; older tasks unchanged)
- **`recurrence: {kind: 'after', unit: 'day' | 'month', interval}`:** N days (1–365) or months (1–12) after the last completion.
- **`source`** (generated tasks only, immutable): `{kind: 'room' | 'device', id, typeKey, templateKey, templateVersion}`.
  - Task id: `r_<roomId>_<templateKey>` or `d_<deviceId>_<templateKey>`.
  - `roomId` = the room (room tasks), or `null` (device tasks follow the device's current room).
- **`estimatedMinutes`:** int 1–600 (generated tasks; editable).
- A **declined** template task is stored archived (`active: false`) and blocks re-creation.

- `name` (1–120, required), `organization` (≤ 120 | null), `email` (≤ 254, basic shape | null), `address` (≤ 300 | null), `notes` (≤ 1000 | null);
- `phones`: ≤ 10 strings `"label|number"` — label 1–30 (no `|` / control characters; `mobile` `home` `work` `whatsapp` `fax` `other` or custom), number ≤ 40 of `+ 0-9 ( ) space . / # * -`;
- `categoryIds`: ≤ 10 unique category ids (ids of removed categories are ignored on display and dropped on the next save);
- `favorite` (bool, **shared** by the household);

- `deleted` (bool), `deletedAt`, `deletedBy` (soft delete);
- `rev` (starts at 1, every change is exactly + 1);
- `createdBy`, `createdAt`, `updatedBy`, `updatedAt`, `schemaVersion` 1.

### V6.4 Batch C: contact pictures and restaurant menus (additive; optional keys)

Two OPTIONAL keys on `homes/{h}/contacts/{contactId}`. Contacts written before 6.4.0-c have neither key and need no migration.

| Key | Type | Limits | Notes |
|---|---|---|---|
| `avatarUrl` | string \| null | https URL, ≤ 500 characters | Shown as a circular avatar. Missing, invalid or broken → initials |
| `menus` | list of strings | ≤ 10 entries, each `"kind|label|url"` | `kind` ∈ `image`, `pdf`, `web`, `drive`; `label` 0–40 characters, without `|` or control characters; `url` as above. The list order is the display order |

- **URL grammar** (identical in `contact-media.js` and `firestore.rules`, enforced by a unit test):
  - `https://` only;
  - a lower-case DNS host with an alphabetic top-level label (no trailing dot): no IP addresses, no bare `localhost`, no credentials or `@` in the authority;
  - not on a prohibited host (rev 2): the local-network suffixes `localhost`, `local`, `localdomain`, `internal`, `intranet`, `lan`, `home`, `home.arpa`, `corp` and `private`, and the wildcard-DNS services `nip.io`, `sslip.io`, `xip.io`, `localtest.me` and `lvh.me`;
  - an optional port;
  - path, query and fragment limited to printable URL characters: no spaces, quotes, `<`, `>`, `\`, `^`, `` ` ``, `{`, `|`, `}` or control characters.
  - This is a syntactic, best-effort check. See SECURITY.md for what it cannot prevent (DNS, redirects).
- **Why strings, not maps:** the same technique as `phones`.
  - **Revision 2:** every element is validated on its own, by index (`menus[0]` … `menus[9]`), with an anchored length pattern and an anchored format pattern. One element is therefore exactly one entry: it cannot carry two entries, and two elements cannot combine into one.
  - Only after that does a single negative check (the host deny-list) run over `menus.join('|')`. It is safe there because the element boundaries are already proven.
  - The Batch C revision 1 check validated the structure on the joined string, which allowed combined and split elements. It is replaced.
- **No bytes:** no Base64 or binary data, no Firebase Storage. Pictures and menus stay on their own hosts.
- **Restaurants:** the Menu section is shown when a live category with key `restaurants` (`s_restaurants`) is assigned.
  - A rename keeps it.
  - Removing the category or un-assigning it hides the section; `menus` is kept.
  - Re-adding the suggested category, or re-assigning it, shows the section again.
- **Imports and merges:** a `.vcf` import never creates media keys; the rules refuse `avatarUrl` or `menus` on `source: 'vcf'` creates. A merge never touches them.
- **Edits:** media changes are ordinary content edits: `contacts.edit`, `rev + 1`, stamped by the caller.
- **Export:** vCard export intentionally excludes `avatarUrl` and `menus` (no `PHOTO`, `LOGO`, `URL` or custom menu lines). Export compatibility with 6.4.0-b is unchanged.
